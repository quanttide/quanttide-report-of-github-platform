# 特殊文件那篇为什么写浅了：一次偷懒复盘

读这篇的人只想知道两件事：这次为什么写浅，下次怎么不重犯。2026-10-14，给案例集写 `gallery/special-files.md`——登记仓库的特殊文件——连改三版才对：第一版凭印象拼了张表，被判「不对」；第二版把「统一」写成「按类型」，又被否；第三版才逐个文件给出文本。本复盘用一句话回答：**我把「写一篇关于某概念的文档」当成了「产出一张看起来对的表」，而「特殊文件」在量潮早是个有定义的词——教程、章程、多个仓的 README 都写了它，我一份都没查。**

## 一、浅在哪

- 凭名字猜内容：文件叫 special-files，就默认内容自明，直接拼了 README / CONTRIBUTING / CHANGELOG / LICENSE 的表。而「特殊文件」是量潮的有定义词：教程《DevOps 实践理念》讲它是「人机协同的事实源」，章程第五条列了它，`quanttide-tech` README 与 `quanttide-data` AGENTS.md 各有一份登记。
- 凭印象定清单：表里没有 `.gitignore`——章程第五条明确把它列为特殊文件；也没写出 `AGENTS.md` 是「上下文入口」这层含义。
- 把「统一」写成「按类型」：第二版才被纠正——特殊文件的**套件统一**，变的是每类仓库的**文本**。
- 只描述、不使用：本仓有写好的 `CONTRIBUTING.md`、`README.md`、`CHANGELOG.md`，我却去「描述」它们（一行「贡献规范：本仓的写法与边界」），而不是把它们**当成文本用**。

## 二、为什么偷懒（根因）

- **命名即答案的错觉**：文件名叫什么，就以为内容自明，跳过「这个词在体系里指什么」。
- **优化「看起来完成」**：一张齐整的表比一段查证更快显出成果——正是前几次才写进案例的老病「排版完整冒充设计完整」。
- **纪律没跨任务迁移**：建仓时我明明先查邻居实物、再动手（还写进了案例），换到写文档却把同一条纪律丢了。

## 三、下次怎么做

1. 写「有名字的概念」前，先在体系里 grep 这个词，找它的既有定义（本仓 / 领域 / 教程 / 章程）。
2. 清单类文档的每一项都要有出处，不凭印象列。
3. 手边有现成文本就用现成的，别重述——「描述」不是「给文本」。

## 四、边界与落地

边界：本篇只谈「写有名字的概念时为什么不查既有定义」，不谈那篇文档具体该长什么样（那是内容问题）。样本是一次连改三版，够了。

落地：`gallery/special-files.md` 已按教程与章程重写——逐个文件给出文本，现成的直接采用。
